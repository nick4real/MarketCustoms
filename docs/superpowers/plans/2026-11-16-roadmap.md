> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. **No commits**: report the changed files instead.

**Goal:** Replace the README-based MVP plan with one living roadmap, `docs/development_plan/ROADMAP.md`, that reflects the current code and the approved feature-led phases 0–9.

**Architecture:** Documentation only. One Markdown file is created, one is deleted, and the README gets a link. No code, config or tests change.

**Tech Stack:** Markdown (GitHub-flavoured, Mermaid allowed).

**Spec:** `docs/superpowers/specs/2026-11-16-roadmap-design.md`

**TDD:** not applicable (docs only).

## Global Constraints

- MVP = Phases 0–4: a seller lists an item, a buyer pays, the seller ships and gets paid, and it's deployed.
- Phase table, demos and technologies exactly as in the spec's "Phase breakdown (approved)" table. Do not reorder, merge or rename phases.
- Target technologies: RabbitMQ, Redis, Elasticsearch, SignalR, Kubernetes, Stripe, Auth0, Kafka, CI/CD. Each must appear in at least one phase.
- No launch concerns in scope: no legal pages, GDPR, VAT/invoices, real KYC, soft launch. Stripe is test mode only. Kubernetes is local `kind` only; a cloud cluster goes in the parking lot.
- Library choices (for example MassTransit vs Wolverine) are listed as **open decisions** in their phase, not settled. Note that MassTransit v9 needs a commercial licence.
- Match the repo's docs style (see `README.md`, `STRUCTURE.md`): plain sentences, tables, sentence-case headings, no emojis.

## Review Focus

- A statement about the current state that the code contradicts (for example, saying CI works, or that listings have a status). Each "current state" claim must match the spec's "Current state" section.
- A technology that appears in the tech table but in no phase's scope, or the other way round.
- A phase "Done when" that can't be checked (vague wording instead of a demoable outcome).
- Content from the old plan that was lost without a decision: outbox, idempotent signature-verified webhooks, reservation timeout, order state machine, RAM advice, `Seeding:Mode` `IfEmpty`.
- Broken relative links (spec, plans, `STRUCTURE.md`).

### Task 1: Write `ROADMAP.md`

**Files:**
- Create: `docs/development_plan/ROADMAP.md`

Sections, in this order:

1. **Title and one-paragraph vision.** A portfolio and learning project. Each technology is learned through a real marketplace feature. The code is kept clean enough to reuse.
2. **How to use this roadmap.** The roadmap is high-level. When a phase starts, it gets its own spec and plan in `docs/superpowers/specs|plans/`, and its status here is updated. An ADR is written for each technology or library choice (the folder is created in Phase 0).
3. **Principles.** Feature-led vertical slices. Every phase ends in a demoable state. Definition of done for a feature: API + validation + tests (unit for domain logic, integration via Aspire) + gateway route + client slice + CI green + docs updated. Run only the services you are working on in the AppHost (RAM advice).
4. **Where we are today.** The spec's "Current state" bullets.
5. **Technology map.** A table with columns: technology | job in MarketCustoms | phase(s). Rows for the 9 target technologies plus existing ones that get extended (Aspire, YARP, OpenTelemetry). The text explains how RabbitMQ, Kafka and Redis each have a separate job.
6. **Phase overview.** The approved table plus a Status column (all `Not started`). A Mermaid `flowchart LR` showing 0→1→2→3→4 as the MVP, then 5–9.
7. **Phase sections 0–9.** Each one uses the same sub-headings: Goal, User story, Services touched, Scope (bullets), Out of scope, New technology, Open decisions, Done when (checkable bullets). Old-plan content goes here:
   - Phase 0: fix `backend-catalog-ci.yml` (branch `main`, path filter typo) or replace it with workflows for every service plus the frontend (`npm run validate`, `npm run test`); write the definition of done; create `docs/adr/`; switch `Seeding:Mode` to `IfEmpty` once real test data exists.
   - Phase 1: listing status lifecycle (Draft, Active, SoldOut, Removed; open decision on Reserved given `StockQuantity`); update and delete endpoints with owner checks; Auth0 roles/permissions (admin on `POST /categories`); deciding how `AccountType` maps to selling rights; Blob image upload via Azurite; Redis cache for the category tree; React seller dashboard.
   - Phase 2: order state machine (Created, PendingPayment, Paid, Shipped, Completed, Cancelled, Refunded); RabbitMQ with outbox; checkout saga; stock reservation with a timeout (decrement `StockQuantity`); Stripe Checkout; idempotent, signature-verified webhooks; basic cancel and refund. Open decisions: messaging library, saga style (orchestration vs choreography).
   - Phase 3: Deliveries with a manual tracking number and buyer confirmation; Stripe Connect Express onboarding (test mode) and payout on confirmation; Notifications consuming events, sending email to Mailpit, and SignalR live updates.
   - Phase 4: Dockerfiles/images to GHCR, Aspire publish → Helm, a `kind` cluster, a GitHub Actions CD job, secrets handling, where MongoDB, SQL Server and RabbitMQ run in the cluster.
   - Phases 5–9 as in the spec table. Phase 9 notes the admin panel (Auth0 admin role from Phase 1).
8. **Parking lot.** Cloud Kubernetes (AKS) or Azure Container Apps via `azd`, a carrier API for Deliveries, a mobile/second client, Azure AI Search, MongoDB Atlas.
9. **Links.** Spec, `README.md`, `STRUCTURE.md`.
